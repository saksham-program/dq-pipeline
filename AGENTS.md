## DQ Pipeline architecture
- Data processing (validation, cleaning, reconciliation) lives in pure TypeScript in `src/lib/dq/engine.ts` with tests in `engine.test.ts`; orchestration and persistence are in `src/lib/dq/runner.ts`. Why: the hosting runtime cannot run Python/FastAPI; keeping the engine pure lets it be swapped for an external Pandas service behind the same `runPipeline` contract.
- Single-user app with no sign-in: every public table has an open RLS policy for anon/authenticated. Why: the product brief explicitly forbids accounts; add auth before exposing to multiple users.
- Original source rows are stored untouched in `datasets.raw_records`; cleaning only affects the accepted copy. Why: traceability of rejected/cleaned rows.
- API ingestion goes through the `fetchApiSource` server function (`api-fetch.functions.ts`), which returns raw JSON text. Why: avoids browser CORS and blocks private-network URLs.
- Run-history cleanup is shared between the Runs and History pages and removes run-linked results before run entries, while preserving datasets and rules. Why: users can clear execution output without losing reusable source configuration.
- Decorative waves are generated SVG in `src/components/dq/Waves.tsx` (one composition per top-level route, colored only by `--wave-*` tokens) and mounted once by `AppShell`. Why: pages stay free of decoration code and both themes restyle the waves through tokens alone.
- Bulk rule management reuses the single engine: templates in `rule-templates.ts` compile to existing rule types (plus `allowed_values`); `rule-suggest.ts` proposes inert drafts; `rule-io.ts` imports/exports JSON and a strictly-parsed SQL export format (pasted SQL is never executed). Persistence goes through `bulkInsertRules` → the `bulk_insert_validation_rules` database function (one transaction, whitelist validation, unique fingerprint index). Why: no second engine, no user-supplied SQL on the database connection, and idempotent imports.
- A run with zero executable rules gets status `not_evaluated` and is excluded from quality metrics. Why: "no rules" must never look like 100% clean data.
- Workspace lifecycle lives in `workspace.ts` (pure, store-injected) with a Supabase adapter in `db.ts` and the SQL in migration `0002`. Fresh Demo auto-reset needs ALL of: demo mode, dev environment, one-time user consent, and a new launch id claimed atomically. Why: the schema has no workspace column, so the app cannot tell user data from demo data — it must ask before deleting, and a refresh/HMR/second tab must never reset. The launch id is kept in its own `workspace_state` table, not `app_settings`, because saving Settings rewrites that whole JSON document.
- Deleting rules never cascades to datasets or history; reset deletes children before parents (`pipeline_runs.dataset_id` is only SET NULL, so runs must be removed explicitly).
- Rule types: only the eight canonical types are stored/executed; template names (`unique`, `date`, …) are aliases normalised by `rule-types.ts` at import, in the editor, and again by the engine before running. Why: the engine used to run an unknown type through `default:` and silently pass every row — now unknown types become an `unsupported_rule` violation and are excluded from coverage. The database function is deliberately NOT alias-aware: the app always sends canonical rules, so the stored schema has one convention.
- Dataset warnings come from `dataset-status.ts` via `<DatasetStatusNotice />` on both Dashboard and Validation Rules. Do not add page-local warning logic.
